# Анализ проекта M8 (chess-duolingo)

Дата: 2026-11-01. Анализ к сборке «админ-панель + дашборды + новые режимы». Чтение кода — свежее, выводы выстроены для читателя отчёта; сырая разведка — в `notes.md`.

## 1. Резюме

M8 — зрелый офлайн-first шахматный тренажёр: собственный поисковый движок, целостная геймификация (XP, стрики, лига, миссии, тетрадь ошибок), два языка, три платформенные обёртки (PWA/Tauri/Capacitor) и дисциплина проверки (`npm run check`, 46 тестов). Главные системные риски — не в геймплее, а в трёх местах: (1) безопасность (хардкод пароля встроенного админа в исходниках и подтверждённый утёк Supabase-токена в git-истории), (2) хранение (весь прогресс игрока живёт только в localStorage конкретного устройства), (3) расхождение витрины с реальностью (README и i18n обещают то, чего в данных нет). Эта сборка закрывает админку, статистику и новые режимы; пункты 1–3 остаются темой отдельных задач (см. `ideas.md`).

## 2. Архитектурная карта

### Слои

| Слой | Где | Что важно знать |
|---|---|---|
| Экраны и роутинг | `src/App.tsx` | Роутинга как библиотеки нет: `type Screen` (10 значений) + `useState`. Новый экран = новое значение union + кнопка в top bar/bottom nav + блок рендера. `SettingsScreen` — монолит внутри `App.tsx` (строки ~404–547) |
| Компоненты | `src/components/` (19 файлов) | Крупные: `ChessPuzzle` (735 строк), `PlayScreen` (412), `PracticeScreen` (258), `ReviewScreen` (183) |
| Состояние | `src/hooks/`, `src/contexts/` | `useProgress` (весь прогресс игрока), `useEngine`, `useCoach`; контексты `Auth`, `I18n` (ru/en, ~188 ключей на язык), `Theme`, `Subscription` |
| Игровое ядро | `src/ai/engine/` | Полноценный перебор: negamax + альфа-бета + итеративное углубление + TT (150k) + quiescence (MVV-LVA), MAX_PLY=96; 8 уровней-персон (depth 1–6, бюджет 120–800 мс, шум/блитц-ошибки на 1–3). Мат гарантированно находится (тесты `engine.tactics.test.ts`) |

| LLM-коуч | `src/ai/coach/` + `supabase/functions/ai-coach` | Кэш ответов (`coach_cache` в Supabase), лимиты (`coach_usage`), офлайн-режим |
| Контент | `src/data/` | 65 задач (lichess-импорт, рейтинг 827–1600), 13 уроков, 13 тем теории, 10 слайдов курса новичка |
| Платформа | `vite.config.ts`, `src-tauri/`, `android/` | PWA через `vite-plugin-pwa` (SW + manifest), Tauri 2, Capacitor 6 |
| Сервер (опционально) | `supabase/` | Auth, `profiles.role` (галочка админа в Profile), `subscriptions` (`plan`, `paid_until`), оплата NOWPayments через edge-функции `create-invoice`/`check-payment`. Нет `.env` → `supabaseEnabled=false` → всё работает локально |

### Потоки данных

1. **Прогресс игрока (главный).** Экран → `useProgress.<мутатор>` → `progress` → `useEffect` пишет `localStorage['chessup-progress:<userId>']` (для гостей и локальных пользователей `id = email`, для Supabase — UUID). При загрузке `normalize()` дозаполняет новые поля, ресетит дневные/недельные миссии и пересчитывает лигу против фейковых ботов. Аутентификация и прогресс слабо связаны: смена режима входа меняет `userId` → «другой игрок».
2. **Ход ИИ.** UI → `useEngine.findBestMove(fen, level)` → `engineClient` → Web Worker → `searchBestMove` → `{san, scoreCp, ...}`. Ошибочные ходы задач стекаются в `progress.mistakes` (хвост 100) → `ReviewScreen` строит «слабые темы».
3. **Деньги.** `PremiumScreen` → `cryptoPay.createInvoice` → edge-функция NOWPayments → `checkPayment` опросом → `SubscriptionContext` (`plan` локально в `chessup-plan:<userId>` или в таблице `subscriptions` с офлайн-кэшем). Промокодов в продукте пока нет — их добавляет эта сборка.
4. **Коуч.** `useCoach` → `coachService` → edge-функция `ai-coach` (или офлайн-заглушка) → кэш.

## 3. Сильные стороны

- **Настоящий движок, а не имитация**: полный перебор с продвинутой отсечкой, 8 различимых персон, покрытие тестами тактики (маты в 1–2 находятся и оцениваются `MATE_SCORE − ply`).
- **Офлайн-first без компромиссов**: без Supabase работает всё, кроме коуча и оплаты; `supabaseEnabled` — единственная точка ветвления.
- **Петля удержания собрана целиком**: стрик, ежедневные миссии, лига с дивизионами, выживание с комбо, тетрадь ошибок с «прорешать слабые темы» — редкая связность для MVP.
- **Инженерная гигиена выше среднего**: delivery gate `npm run check` (lint oxlint + tsc + vitest), пороги coverage 85/75 по `src/ai/**`, договорённости зафиксированы в ADR и `docs/ARCHITECTURE.md`.
- **i18n и темы — первоклассные**, не прикручены потом: ~188 ключей на язык, `data-theme` на `<html>`, токены в `@theme` Tailwind v4.

## 4. Слабые стороны

- **Хрупкость хранилища.** Прогресс — один JSON в localStorage: очистка браузера = потеря всего; между устройствами не переносится (TransferCard с кодом `CHUP1.` — ручной костыль); хвосты mistakes 100 / партий 20 ограничивают аналитику. Для дашборда это значит: метрики честны только в пределах устройства.
- **Монолиты UI.** `App.tsx` (547+ строк с настройками) и `ChessPuzzle` (735) растут линейно с каждой фичей; этой сборкой добавляются три экрана — без рефакторинга роутинга монолит продолжит расти.
- **Тонкий контент-слой.** 65 задач на 7 тем; подсказки шаблонные с дословными дублями (до 4 повторов одной заготовки) — сборка их переписывает, но генерация/импорт новых задач остаётся ручным.
- **Тесты только на ядре.** Все 46 тестов — `src/ai` и `src/game`; ни одного компонентного или теста хуков прогресса, хотя именно `useProgress.normalize()` — самое рискованное место при миграциях схемы.
- **Два стиля стилизации.** Tailwind-утилиты соседствуют с ~десятками inline `style={{background:'var(--legacy-alias)'}}`; легаси-алиасы CSS-переменных держатся для старого кода — постепенная унификация не начата.
- **Ручная эксплуатация.** Никакого CI в репозитории; админ-скрипты разрозненны (39 mjs-файлов), часть untracked.

## 6. Выводы для отчёта

1. Продукт технически здоров: ядро (движок, прогресс, геймификация) спроектировано связно и покрыто тестами; узкое место — не код, а операционка (секреты, git-история, README).
2. Критический путь безопасности — флаги 1–2 из §5: пароль админа убирает эта сборка, ротацию токена и чистку истории нужно сделать руками сразу после демо.
3. Следующая большая ставка — перенос прогресса в облако: он одновременно снимает риск потери данных, делает честной лигу и даёт админ-панели сквозные метрики вместо локальных.
4. Витрина (README, цифры, цены) должна правиться в том же PR, что меняет данные, — сейчас она отстаёт на один релиз и подрывает доверие на демо.
