# ADR-0008: Блокировка пользователей — profiles.banned + RLS по роли admin

**Статус:** принято (2026-11-01)

## Контекст

Вкладка «Пользователи» должна уметь блокировать Supabase-пользователей;
заблокированный при входе получает понятную ошибку. Клиент ходит с публичным
anon-ключом, серверной части у панели нет; в Supabase уже есть таблица
`profiles` с колонкой `role`.

## Решение

Миграция добавляет `profiles.banned boolean not null default false` и
SQL-функцию `is_admin()`; право на обновление `banned` даёт RLS-политика
только строке с `role='admin'`, причём админ-грант — только на колонку
`banned` (строку целиком админ не редактирует); читать `banned` может сам
пользователь и админ. Проверка на входе: после успешного `signInWithPassword`
выбирается `banned`; `true` → `signOut()` и ошибка `banned` с i18n-ключом
`loginBanned`.

## Почему

- **Блокировка только на клиенте** (флаг/проверка в приложении) — отклонена:
  anon-ключ публичен, заблокированный зайдёт минуя приложение прямым вызовом
  API. Единственное место принудительного исполнения без собственного
  сервера — политики Postgres.
- **Отдельная таблица забаненных** — отклонена: та же работа с RLS, но лишний
  запрос при входе и ещё один шейп данных; колонка в уже используемой
  `profiles` дешевле.

## Последствия

- Блокировка действует со следующего входа: уже выданная сессия не рвётся
  на лету.
- Роль `admin` в Supabase становится привилегией, дающей право блокировать
  людей, — выдавать её надо осознанно.
- RLS-политики — SQL в миграции: юнит-тесты приложения их не ловят,
  проверяется на живой базе.
- Колонка-only грант значит: админ через панель не может править username
  и прочие поля — и это желаемое поведение, а не недоработка.
