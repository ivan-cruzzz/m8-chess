# ADR-0001: Шахматный движок в Web Worker с бюджетом времени

**Статус:** принято (2026-08-21)

## Контекст

Движок (negamax на chess.js) выполнялся синхронно на главном потоке:
уровень 8 в миттельшпиле блокировал UI на ~7,6 с. PWA-офлайн, Tauri и
Capacitor-WebView накладывали ограничение: без сервера, без тяжёлых
зависимостей.

## Решение

1. Перенести поиск в Web Worker (`new Worker(new URL(...), { type: 'module' })`
   — Vite собирает и прекэшит чанк, работает во всех целевых WebView).
2. Итеративное углубление с жёстким бюджетом времени на уровень
   (120–800 мс): ход гарантированно возвращён по истечении бюджета,
   первая итерация (глубина 1) всегда завершается.
3. Отмена — по id на клиенте: воркер синхронно занят до конца поиска,
   сообщение `stop` физически не может быть обработано раньше; максимум
   занятости воркера ограничен бюджетом.
4. Fallback: без Worker — синхронный поиск в setTimeout с тем же бюджетом
   (экзотические старые WebView; покрывается тестами).
5. TT-ключ — точная строка из первых 4 полей FEN. Инкрементальный Zobrist
   невозможен поверх публичного API chess.js (нет доступа к внутреннему
   представлению); строковый ключ даёт ноль коллизий при приемлемой цене.
   Матовые оценки в TT не кладутся (упрощает корректировку на ply).
6. Уровни 1–8 — «персоны» `{depth, timeBudgetMs, noise, blunderChance}`:
   слабые уровни играют по-человечески плохо (шум оценки, случайные зевки),
   сильные — полная сила.

## Последствия

- Главный поток свободен во время поиска; UI не «замерзает».
- Уровень 8: ~7,6 с → ~0,9 с на эквивалентной позиции, маты в 1–2 решаются
  (старая оценка их не видела — только материал).
- `src/game/engine.ts` остаётся deprecated-обёрткой для обратной совместимости.
- Этап 5 (опционально): собственный 0x88-борд + инкрементальный Zobrist
  вместо chess.js-адаптера, если понадобятся глубины 7+.
